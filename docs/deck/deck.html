02Problem & why it matters

92% of bug reports are missing a step you need to reproduce them.

A solo maintainer at a small software agency, on the Monday morning a client emails “the checkout is broken, please fix ASAP”, needs a way to turn that one sentence into a test that fails for the reason the client is describing — before anyone touches the code.

92% of studied bug reports are missing at least one step needed to reproduce them.
Developers spend 35–50% of their working time validating and debugging.

03Solution overview

One differentiator, and it is a refusal.

Repro reads the complaint, searches the code, writes a test that fails for the reported reason, and only then proposes a patch — which it accepts solely when that test goes green and the project’s existing suite stays green.

NO REPRODUCTION No patch. The agent says so and asks the client a question in their own words.
RED → GREEN + GREEN SUITE The only route to an accepted patch. pytest is not an LLM; its verdict is never overridden.
HUMAN PRESSES MERGE Output is a patch and a PR body, plus a plain-language reply to the person who complained.

Enforced in code at RunRecord.check_invariants — src/repro/contracts.py:277 — and proved by tests/test_graph.py:473.

Safety property + pointers: README.md §6, verified against source line numbers. Suite: 572 tests, make test.

Where an agent earns its place over a script

  • →Decides how many questions to ask. A well-specified report gets zero; “it’s broken” gets one round of at most three.
  • →Revises a wrong hypothesis using evidence from the world. The repro test running green is the observation that the hypothesis was wrong.

  • →Verifies its own work against reality. pytest is not an LLM.

The vocabulary gap answers “why no vector database?” Our corpus is one repository, in a temp directory, for sixty seconds, and OpenSearch’s minimum always-on capacity costs hundreds a month. Ten hand-written synonyms you can read beat an embedding model here; identifiers split on snake_ and camelCase do the rest; and retrieval returns a function, not a file, so the model gets a symbol rather than a page dump.

Have these ready but keep them off the slide: the agent’s whole surface is one Protocol, seven methods, four capabilities — search, write under tests/, run pytest, apply/revert a diff. No shell, no network, no install; a real project’s dependencies go into a per-run venv before START, by a function no node can reach. Both money caps are checked before each call against a pessimistic estimate, not after — the call that breaks the cap is the one you wanted to stop.

Say “one model per run” and nothing more about model choice. DO NOT CLAIM docs/ARCHITECTURE.md describes escalating to Sonnet on the last attempt; that is not built. 06Innovation & uniqueness

“Doesn’t Copilot already do this?”

GitHub Copilot’s coding agent, Devin and gitagent all fix bugs from issues. Three differences, and all three are structural.

  1. 01

    They begin where our person is stuck.

    Copilot’s agent, Devin and gitagent all take a GitHub issue as input. Writing that issue is the work our person cannot get the client to do. 92% of real reports are missing a reproduction step; someone has to infer them, and today that someone is a human on a Monday morning.

  2. 02

    They optimise for a patch. We refuse to emit one without a failing test first.

    Not a stylistic preference — the safety property, enforced in code. A recent study found 12.3% of LLM-generated bug-report summaries contained fabricated content. A plausible patch for an unreproduced bug is the most expensive artefact in software: it closes the ticket and leaves the bug.

  3. 03

    They serve the developer. We close the loop with the person who complained.

    Every run ends with a plain-language reply that describes what we reproduced in the client’s own words. The agency’s problem is not only the bug; it is the email thread.

All three arguments and the competitor list: docs/PROBLEM_STATEMENT.md, “The Solved Problem test, answered properly”. 12.3%: arXiv:2605.24137.

09Roadmap

Three steps, in the order the evidence justifies.

NEXT

A GitHub App, and webhooks

Today the only thing we do with GitHub is clone, one repository per run. An App with issue and comment webhooks means the client’s email lands and the reproduction is waiting when the maintainer opens their laptop — which is the Monday morning the problem statement is about.

THEN

Beyond Python and pytest

The safety property is language-agnostic — it needs a runner that reports pass, fail and error distinctly, because is_reproduction treats an error as “we learned nothing”, never as a reproduction. Jest and Go’s testing both do. Everything language-specific sits behind one Protocol of seven methods, so a second language is a new runner, not a new architecture.

THE INTERESTING ONE

Learning which hypotheses paid off

Every run already stores a full RunRecord: which files the localiser proposed, and which one the reproduction actually landed in. That is a labelled dataset generated as a by-product of doing the work — enough to rank candidates by what has worked in this repository before.

Current limits: “What we are explicitly NOT building”, docs/ARCHITECTURE.md. Sandbox protocol: graph/sandbox_seam.py:85–98, seven methods. Error ≠ reproduction: agents/_common.py:81. Stored records: RunRecord, contracts.py:260.
